## 1. 文档说明

### 1.1 文档目的

本文档用于明确个人 Markdown 笔记管理工具的建设目标、使用场景、功能范围、非功能要求、数据约束、版本规划和验收标准，作为后续原型设计、技术选型、任务拆分和开发验收的基础。

### 1.2 名词约定

| 名词 | 含义 |
| --- | --- |
| NoteHub | 当前 Markdown 笔记目录。原始描述中的 `NodeHub` 按现有目录名称理解为 `NoteHub` |
| 工作区 | 用户授权给应用管理的一个本地目录，本项目首个工作区为 `NoteHub` |
| 笔记 | 工作区中的 Markdown 文件，主要扩展名为 `.md` |
| 附件 | 图片、PDF、表格、脑图、代码文件等被笔记引用或与笔记共同管理的文件 |
| 元数据 | 文件路径、名称、修改时间、标题、标签、Front Matter、Git 状态等描述性信息 |
| 索引库 | 为搜索和统计建立的派生数据，可随时从文件重新生成，不是笔记的事实来源 |
| 外部修改 | 用户通过 VS Code、Git、脚本或其他工具对工作区文件产生的变更 |

### 1.3 需求优先级

| 级别 | 含义 |
| --- | --- |
| P0 | MVP 必须具备，没有该能力就无法解决核心问题 |
| P1 | 首个稳定版应具备，明显提升日常使用效率 |
| P2 | 后续增强能力，验证 MVP 后再建设 |
| P3 | 长期设想，不进入近期开发承诺 |

## 2. 现状调研

### 2.1 当前工作方式

用户是多年后端开发工程师，已经形成稳定的文件型知识管理方式：

1. 使用 Markdown 编写和长期保存笔记。
2. 把笔记作为项目目录管理，使用 Git 记录版本并在多台电脑之间同步。
3. 主要使用 VS Code 编辑，依赖 Markdown All in One、Markdown Preview Enhanced 等插件。
4. 使用 PicGo 将粘贴或截图图片上传至阿里云 OSS，并在 Markdown 中保存远程图片链接。
5. 通过目录、文件名、索引文档和少量 Front Matter 管理内容。

### 2.2 当前仓库特征

截至 2026-10-03，对当前 `NoteHub` 目录的抽样统计如下：

| 项目 | 现状 |
| --- | --- |
| Markdown 文件 | 约 476 个 |
| 一级业务目录 | 约 15 个 |
| 图片引用 | 224 个 Markdown 文件中存在图片语法 |
| 外部链接 | 362 个 Markdown 文件中存在 HTTP/HTTPS 链接 |
| 待办项 | 137 个 Markdown 文件中存在任务列表 |
| Mermaid | 8 个 Markdown 文件中存在 Mermaid 图表 |
| Wiki Link | 3 个 Markdown 文件中存在 `[[...]]` 链接 |
| Front Matter | 已开始使用，但字段尚未在所有笔记中统一 |
| 其他文件 | 同时存在 JS、CSS、HTML、Shell、Python、Excel、XMind、JMeter 等资料 |

当前目录已经体现出清晰的内容生命周期：

```text
00-inbox       临时收集
01-index       索引入口
02-organize    AI 整理结果
10-life        生活记录
20-knowledge   长期知识
30-finance     投资与复盘
40-publish     自媒体内容生产线
50-learning    学习资料
60-work        工作文档
70-projects    项目专题
80-resources   资料资源
90-archive     历史归档
99-system      规则、模板和脚本
assets         附件
```

其中 `40-publish` 已经按想法、草稿、编辑、待发布、已发布等状态划分目录；`00-inbox` 存在定期清理需求；`99-system` 已经保存命名规范、Git 规则、笔记流程和模板。这些现有约定应被应用读取和利用，而不是另建一套互相冲突的规则。

### 2.3 主要痛点

| 编号 | 痛点 | 影响 |
| --- | --- | --- |
| PAIN-01 | 文件数量和目录层级增长后，仅靠 VS Code 资源管理器定位较慢 | 查找、回顾和整理成本持续上升 |
| PAIN-02 | 文件夹分类只能表达一个维度，同一笔记难以按主题、状态、来源等多维度查看 | 内容容易被目录“埋住” |
| PAIN-03 | 全文搜索、标题搜索、标签过滤、时间过滤分散在不同操作中 | 找回信息的效率不稳定 |
| PAIN-04 | `00-inbox`、草稿、待发布等状态依靠人工浏览目录 | 容易积压，缺少工作流视图 |
| PAIN-05 | 新建、重命名、移动、归档文件后，需要人工检查内部链接和图片路径 | 整理有破坏链接的风险 |
| PAIN-06 | Git 对日常笔记很有价值，但查看变更、提交、同步和处理冲突需要离开笔记上下文 | 多设备同步操作割裂 |
| PAIN-07 | 远程 OSS 图片、本地附件、外部网页图片混合存在 | 可用性、失效风险和迁移难度不可见 |
| PAIN-08 | VS Code 擅长编辑代码和文件，但不擅长内容看板、统计、回顾和知识关联 | 管理视角不足 |
| PAIN-09 | 笔记可能包含账号、工作、财务等敏感信息 | 不适合默认上传第三方云服务或建立公共在线系统 |

## 3. 产品定位

### 3.1 一句话定位

一个本地优先、文件兼容、Git 友好的 Markdown 笔记工作台，用于在不改变现有文件体系的前提下，提升笔记的查找、浏览、整理、关联和同步效率。

### 3.2 核心原则

1. **文件是唯一事实来源**：Markdown 和附件继续保存在现有目录中，不强制迁移到数据库。
2. **兼容已有工具**：用户可以随时继续使用 VS Code、PicGo、Git CLI 和其他脚本。
3. **本地优先**：默认不上传笔记正文、索引和搜索记录至任何第三方服务。
4. **渐进增强**：没有 Front Matter、标签或特殊语法的普通 Markdown 也能正常使用。
5. **安全可逆**：移动、重命名、删除、批量修改前给出影响范围，并尽量支持撤销或恢复。
6. **缓存可重建**：搜索索引、缩略图和统计数据损坏时，可以从工作区完整重建。
7. **不接管一切**：首版重点解决管理问题，不以完全替代 VS Code 为目标。

### 3.3 产品目标

| 编号 | 目标 | 建议衡量方式 |
| --- | --- | --- |
| OBJ-01 | 降低笔记定位成本 | 80% 的已知笔记可在 10 秒内找到 |
| OBJ-02 | 提高日常整理效率 | Inbox 单条笔记可在 3 次主要操作内完成归档 |
| OBJ-03 | 降低文件操作风险 | 重命名/移动前可看到受影响引用，失败不产生半完成状态 |
| OBJ-04 | 保持工具自由 | 应用外修改能自动同步，退出应用后文件仍可独立使用 |
| OBJ-05 | 简化 Git 日常操作 | 常规查看、提交、拉取、推送可在应用内完成 |
| OBJ-06 | 支持持续演进 | 新的目录、模板、Front Matter 字段无需修改核心代码即可接入 |

### 3.4 非目标

以下内容不进入 MVP：

- 构建类似 Notion 的多人实时协同平台。
- 把 Markdown 全量迁移到私有数据库格式。
- 自建完整 Git 托管服务。
- 替代 VS Code 的全部高级编辑、插件和终端能力。
- 首版支持公网直接暴露和多用户权限系统。
- 首版提供 AI 自动改写、问答或向量知识库。
- 首版承担博客发布、微信公众号发布等完整内容分发能力。
- 首版自动整理或改写所有历史笔记。

## 4. 用户与使用环境

### 4.1 用户角色

#### 角色 A：笔记库所有者

- 唯一的核心角色。
- 熟悉文件系统、Markdown 和 Git。
- 需要在多台电脑上使用同一仓库。
- 既需要快速记录，也需要定期整理、写作和复盘。
- 能理解 Git 冲突，但希望应用避免制造不必要的冲突。

#### 角色 B：只读访问者（后续）

- 用户本人在手机、平板或其他设备上临时浏览。
- 只允许搜索、浏览和预览，不直接修改文件。
- 仅在未来启用局域网或安全远程访问后存在。

### 4.2 运行环境

- 首版桌面环境：macOS、Windows。
- 后续可评估 Linux。
- 笔记目录是本地 Git 工作树，可能包含未提交变更。
- Git 仓库根目录可能位于 `NoteHub` 的上级目录，因此工作区与 Git 根目录不能假定相同。
- 同一批文件可能被 VS Code、Git、脚本和本应用同时访问。
- 图片主要来自阿里云 OSS，也可能引用其他网站或本地相对路径。

## 5. 关键使用场景

### 5.1 快速找到一篇旧笔记

1. 用户打开应用，焦点默认位于全局搜索框。
2. 输入标题片段、正文关键词或路径关键词。
3. 应用实时显示结果，并高亮命中位置。
4. 用户可按目录、文件类型、标签、修改时间、Git 状态过滤。
5. 点击结果后在当前窗口预览，必要时跳转到 VS Code 编辑。

### 5.2 清理 Inbox

1. 用户进入“收集箱”视图，看到待整理数量和按时间排序的内容。
2. 选中一篇笔记，在右侧预览内容。
3. 选择目标目录、状态或常用归档动作。
4. 应用展示移动后的路径以及可能受影响的链接。
5. 用户确认后完成移动，列表自动更新。

### 5.3 新建知识笔记

1. 用户点击“新建笔记”。
2. 选择 `99-system/templates/knowledge-note.md` 模板。
3. 输入标题、目标目录和必要元数据。
4. 应用按命名规则生成文件并打开编辑器。
5. 保存后立即进入索引，并显示为 Git 未提交文件。

### 5.4 推进一篇发布文章

1. 用户进入“发布流程”看板。
2. 看到想法、草稿、编辑、待发布、已发布等列。
3. 将文章从草稿移动到编辑中。
4. 应用实质上执行受控文件移动，并记录 Git 变更。
5. 用户可以继续在内置编辑器或 VS Code 中修改。

### 5.5 完成一次 Git 同步

1. 用户看到顶部 Git 状态提示。
2. 打开变更列表，按文件查看新增、修改、删除、重命名和差异。
3. 选择本次要提交的文件，填写提交说明并提交。
4. 应用在拉取前提示当前未提交变更和可能风险。
5. 无冲突时完成拉取和推送；有冲突时停止自动操作并给出清晰指引。

### 5.6 粘贴一张图片

1. 用户在编辑器中粘贴截图或拖入本地图片。
2. 应用按配置选择 PicGo/OSS 上传或保存至本地附件目录。
3. 上传成功后在光标位置插入标准 Markdown 图片链接。
4. 上传失败时保留原始图片或临时文件，不插入无效链接，并允许重试。

### 5.7 在 VS Code 中修改后回到应用

1. 用户从应用中选择“在 VS Code 中打开”。
2. 用户在 VS Code 完成修改并保存。
3. 应用通过文件监听发现变化。
4. 若应用内没有未保存编辑，自动刷新预览和索引。
5. 若应用内存在未保存内容，提示外部冲突，禁止静默覆盖。

## 6. 信息架构与页面规划

### 6.1 主导航

建议首版采用以下主导航：

| 页面 | 主要用途 | 优先级 |
| --- | --- | --- |
| 首页/工作台 | 最近笔记、收藏、Inbox 数量、待办、Git 状态、快捷入口 | P1 |
| 文件 | 按真实目录树浏览和管理全部文件 | P0 |
| 搜索 | 全文检索、过滤、结果预览 | P0 |
| 收集箱 | 聚合 `00-inbox` 并执行快速整理 | P0 |
| 发布流程 | 按 `40-publish` 子目录展示内容状态 | P1 |
| 任务 | 聚合 Markdown 任务列表 | P1 |
| Git | 查看变更、差异、提交与同步 | P1 |
| 设置 | 工作区、忽略规则、编辑器、模板、图片、Git 配置 | P0 |

### 6.2 主界面布局

桌面端建议采用三栏结构：

```text
┌─────────────┬────────────────────────┬───────────────────────────┐
│ 主导航/目录 │ 文件列表或搜索结果     │ Markdown 预览/编辑         │
│             │                        │                           │
│ 工作区      │ 标题、路径、摘要       │ 面包屑、元数据、正文       │
│ 收藏/最近   │ 修改时间、标签、状态   │ 目录大纲、反向链接         │
└─────────────┴────────────────────────┴───────────────────────────┘
```

要求：

- 左右栏可折叠，中间栏宽度可调整。
- 支持深色/浅色主题和跟随系统。
- 窗口较窄时退化为单栏分层导航，而不是横向压缩到不可用。
- 搜索、预览和文件操作尽量不跳出当前上下文。

## 7. 功能需求

## 8. 业务规则

| 编号 | 规则 |
| --- | --- |
| BR-01 | Markdown 正文及附件是源数据，数据库记录只能作为缓存或派生数据 |
| BR-02 | 应用不得在用户未确认时批量重写 Markdown 格式 |
| BR-03 | 解析失败的 Front Matter 必须保留原文，并提示用户修复 |
| BR-04 | 未知 Markdown 语法应尽量原样保存，不应因编辑器解析失败而丢失 |
| BR-05 | 文件移动、重命名和删除不得越出授权工作区；Git 检查可只读访问其仓库根目录 |
| BR-06 | 删除优先可恢复；永久删除必须二次确认并明确不可恢复性 |
| BR-07 | 路径比较必须兼容 macOS/Windows 的大小写、分隔符和非法字符差异 |
| BR-08 | 远程图片或链接暂时不可访问时，不得自动从 Markdown 删除引用 |
| BR-09 | 应用不得假定所有目录和字段都使用英文，也不得破坏中文文件名 |
| BR-10 | 应用发现 Git 冲突文件时，禁止自动覆盖冲突标记 |
| BR-11 | 自动更新 `updated` 字段必须由用户显式开启，避免每次保存产生无意义 Git diff |
| BR-12 | 模板是普通 Markdown 文件，应用读取模板但不发明私有模板格式 |

## 9. 数据需求

### 9.1 数据分层

```text
源数据层：Markdown、附件、目录、Git 元数据
    ↓ 扫描与解析
索引层：全文索引、标题、标签、链接、任务、访问记录
    ↓ 查询与聚合
视图层：目录树、搜索、Inbox、看板、任务、统计
```

### 9.2 核心实体

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| Workspace | id、rootPath、gitRoot、ignoreRules | 工作区配置 |
| Document | path、title、extension、size、mtime、hash、frontMatter | 文件索引 |
| Heading | documentId、level、text、anchor、line | 文档大纲与跳转 |
| Tag | name、source、count | Front Matter 或未来扩展标签 |
| Link | source、target、type、line、status | 文档、图片、外部链接关系 |
| Task | documentId、line、text、checked、context | Markdown 任务 |
| GitStatus | path、status、staged、conflicted | Git 派生状态 |
| Favorite | workspaceId、path、order | 应用个性化数据 |
| Recent | workspaceId、path、openedAt | 最近访问记录 |
| SavedQuery | name、query、filters | 智能视图，后续能力 |

### 9.3 索引存储要求

- 索引数据库建议使用本地 SQLite/FTS 或同类嵌入式方案。
- 索引文件不应进入 Git；优先保存在操作系统应用数据目录。
- 索引记录应使用工作区相对路径，减少不同电脑绝对路径不同带来的问题。
- 文件内容变更后使用时间戳、大小和内容哈希辅助判断是否需要重新索引。
- 删除工作区配置时只删除应用索引和设置，不删除真实笔记。
- 收藏、最近访问等仅本机数据默认不写入笔记；未来可提供显式同步选项。

### 9.4 Markdown 兼容性

首版最低兼容范围：

- UTF-8 中文文件和路径。
- YAML Front Matter。
- CommonMark 与 GitHub Flavored Markdown。
- 表格、任务列表、围栏代码块和语言标识。
- Mermaid 围栏代码块。
- 标准 Markdown 链接和图片。
- 相对路径、绝对 HTTP/HTTPS URL。
- 基础 Wiki Link。

对于 Markdown Preview Enhanced 特有语法，应遵循“可编辑、尽量预览、绝不破坏”的顺序；无法渲染不等于可以重写或删除。

## 10. 非功能需求

### 10.1 性能

以下指标以当前约 500 篇 Markdown 为基线，同时为未来增长到 10,000 篇预留空间：

| 编号 | 指标 |
| --- | --- |
| NFR-PERF-01 | 500 篇规模下，已有索引的冷启动目标不超过 3 秒 |
| NFR-PERF-02 | 普通搜索首批结果目标在 300 毫秒内返回 |
| NFR-PERF-03 | 打开普通 Markdown 预览目标在 300 毫秒内呈现主体内容 |
| NFR-PERF-04 | 文件保存后 2 秒内可在搜索中命中 |
| NFR-PERF-05 | 全量重建索引时界面保持可用，并显示可取消的进度 |
| NFR-PERF-06 | 目录树采用按需加载，不能因大量附件阻塞主界面 |

### 10.2 可靠性与数据安全

- 文件保存必须避免写出空文件或截断文件。
- 写入前检测磁盘文件版本是否已变化。
- 应用异常退出后，不应损坏已保存文件；未保存草稿应尽可能恢复。
- 批量文件操作保留操作日志，并支持在可行范围内撤销。
- 索引损坏不影响原始笔记，用户可一键重建。
- 每个会改动文件的功能都需要覆盖失败中断测试。

### 10.3 安全与隐私

- 默认只监听本机回环地址，不对局域网或公网开放服务。
- 若使用本地 Web 服务，必须防止目录穿越、任意文件读取和任意命令执行。
- Markdown HTML 渲染需要清理危险标签和属性，默认禁止脚本执行。
- 外部链接和远程图片应避免把本地文件内容、Token 或 Referrer 泄露给第三方。
- Git 凭据、PicGo/OSS 凭据交给系统凭据链、现有 CLI 或 PicGo 管理。
- 日志不得记录笔记全文、剪贴板图片、密码、Token 或私钥。
- 未来开放远程访问时，必须另行设计身份认证、HTTPS、授权与审计，不能直接复用本地无认证模式。

### 10.4 兼容性与可移植性

- MVP 同时支持 macOS 和 Windows。
- 路径处理逻辑从第一版就应避免绑定 POSIX，便于后续支持 Windows。
- 不强制用户安装特定 VS Code 插件。
- 不要求仓库使用特定 Git 托管平台。
- 应用卸载后，所有 Markdown 和附件仍可由任何文本编辑器使用。

### 10.5 可用性

- 高频动作应支持快捷键。
- 删除、覆盖、批量移动、Git 拉取等高风险动作必须清晰反馈。
- 错误信息应包含“发生了什么、哪些文件受影响、如何恢复或重试”。
- 长任务应显示进度并允许取消；取消后保持一致状态。
- 空状态应给出下一步入口，例如“选择工作区”“新建笔记”“重建索引”。

### 10.6 可维护性与可测试性

- 文件系统、Markdown 解析、索引、Git、图片上传应模块化，避免 UI 直接执行底层命令。
- 所有文件写操作集中经过统一安全层。
- Git 和 PicGo 命令参数必须结构化传递，禁止拼接不受信任的 Shell 字符串。
- 关键模块提供单元测试；移动、冲突、外部修改等场景提供集成测试。
- 应准备包含中文路径、空格、特殊字符、坏 Front Matter、超长文档的测试工作区。

## 11. MVP 范围

### 11.1 MVP 必须交付

MVP 聚焦“找得到、看得好、理得动、不破坏”：

1. 选择并安全打开本地工作区，兼容 macOS 和 Windows 路径。
2. 扫描 Markdown 与常见附件，尊重忽略规则。
3. 真实目录树、文件列表、面包屑和最近打开。
4. 文件名、路径、标题和正文全文搜索，支持基础过滤与高亮。
5. Markdown 预览，包括 GFM、代码高亮、任务列表、Mermaid、远程/本地图片。
6. 新建笔记、读取现有模板、基础编辑、保存、在 VS Code 打开。
7. 文件重命名、移动、归档和可恢复删除。
8. Inbox 聚合与快速移动。
9. 文件外部变更监听和未保存冲突保护。
10. 索引重建、基础设置和错误诊断。

### 11.2 MVP 明确不做

- 完整 Git 图形客户端。
- 发布流程看板拖拽。
- 批量编辑 Front Matter。
- 反向链接、链接健康检查和附件清理。
- 应用内直接配置阿里云 OSS AccessKey。
- PDF/Office/XMind 正文索引。
- AI 问答、自动分类、自动摘要。
- 移动端和公网访问。

### 11.3 MVP 完成定义

只有同时满足以下条件才算完成：

- 能直接打开现有 NoteHub，无需迁移或批量改写文件。
- 现有中文路径、远程 OSS 图片、Mermaid 和任务列表可正常浏览。
- VS Code 外部修改能在应用内刷新。
- 新建、编辑、移动和删除经过异常中断测试，不损坏原文件。
- 搜索性能达到本文件的基础指标。
- 已完成备份副本上的真实仓库回归测试。
- 应用关闭后，所有笔记仍能由 VS Code 正常打开和提交。

- Markdown 预览、大纲和外部打开。
- 文件监听与索引重建。

此阶段不写原文件，风险最低，也最适合快速获得真实使用反馈。

### 12.2 第 1 阶段：MVP 管理版

- 新建与基础编辑。
- 模板新建。
- 重命名、移动、归档、废纸篓。
- Inbox 快速整理。
- 外部修改冲突保护。
- 最近使用和收藏。

### 12.3 第 2 阶段：工作流与 Git 版

- Git 状态、diff、选择提交、拉取和推送。
- 发布流程看板。
- 任务聚合。
- Front Matter 和标签管理。
- PicGo 粘贴上传。
- 反向链接与坏链检查。

### 12.4 第 3 阶段：桌面与局域网版

- macOS、Windows 一键安装包。
- 局域网显式开启、认证和只读访问。
- 手机、平板响应式浏览。
- 敏感内容受保护区域。

### 12.5 第 4 阶段：高级编辑与智能增强版

- 保存查询和自定义仪表盘。
- PDF/Office 内容索引。
- 链接与附件健康报告。
- 重复内容检测。
- 可选的本地 AI 摘要、问答、标签和归类建议。
- 只读移动端或安全远程浏览。

## 13. 技术形态建议

### 13.1 推荐方案

首版采用“本地服务 + Web UI”的本地优先架构，稳定后封装为一键安装的桌面客户端：

```text
浏览器或桌面壳
    ↓ 本机 API / IPC
本地应用服务
    ├── 文件系统安全层
    ├── Markdown 解析与渲染
    ├── SQLite/FTS 搜索索引
    ├── 文件监听
    ├── Git 适配器
    └── PicGo 适配器
         ↓
NoteHub 文件 + 系统 Git + PicGo/OSS
```

原因：

- 后端开发背景更容易快速实现和维护本地服务。
- Web UI 开发效率高，也便于以后增加局域网只读访问。
- 浏览器页面本身无法稳定获得完整文件系统、Git 和 PicGo 能力，因此不能做成纯静态前端。
- 文件访问、命令调用和密钥边界可以集中在本地服务层管理。
- 后续若需要安装包、系统菜单、文件关联和更好的跨平台体验，可用 Tauri/Electron 等桌面壳封装，但这不是 MVP 的前置条件。

### 13.2 备选方案比较

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 纯浏览器静态页面 | 部署简单 | 文件系统、Git、监听、PicGo 能力受限 | 不适合核心需求 |
| 本地服务 + Web UI | 开发快、能力完整、便于调试 | 需要启动本地服务；浏览器体验略像管理后台 | MVP 推荐 |
| Tauri 桌面应用 | 包体小、系统能力好、跨平台 | 引入 Rust/桌面工程复杂度 | 稳定版可考虑 |
| Electron 桌面应用 | 生态成熟、编辑器组件丰富 | 包体和内存较大 | 若追求成熟编辑体验可选 |
| VS Code 扩展 | 与现有编辑环境融合 | 难以提供独立工作台和未来多端能力 | 可作为后续辅助入口 |

### 13.3 技术选型约束

本需求阶段不锁定具体框架，但选型必须满足：

- 支持成熟的 Markdown AST 解析与安全渲染。
- 支持中文全文搜索或可替换的搜索适配层。
- 支持可靠的跨平台文件监听。
- 支持原子写入和废纸篓能力。
- Git 调用可以复用系统 Git。
- UI 与文件系统之间有明确安全边界。
- 所有索引都可以重建，不形成数据锁定。

## 14. 验收场景

### AC-01：首次打开现有工作区

```gherkin
Given 用户选择当前 NoteHub 目录
When 应用首次扫描工作区
Then 应显示扫描进度并完成索引
And 目录中的 Markdown 文件可浏览
And 不修改任何原始文件
And 不索引 .git 和默认忽略目录
```

### AC-02：中文全文搜索

```gherkin
Given 工作区存在标题或正文包含“Deployment”的中文技术笔记
When 用户输入关键词并限制到 02-organize/DevOps
Then 首批结果在目标时间内显示
And 每个结果包含真实路径与命中摘要
And 点击结果可定位到对应文档
```

### AC-03：兼容 Markdown 内容

```gherkin
Given 一篇笔记包含表格、任务列表、代码块、Mermaid 和 OSS 图片
When 用户打开预览
Then 上述内容均可阅读
And 远程图片失败不会导致整个页面失败
And 文档中的脚本不能执行
```

### AC-04：安全移动笔记

```gherkin
Given 一篇 Inbox 笔记将被移动到知识库
And 目标目录不存在同名文件
When 用户确认移动
Then 文件出现在目标目录且内容不变
And 原路径不再存在
And 搜索索引和列表同步更新
And Git 能看到对应变更
```

### AC-05：目标重名

```gherkin
Given 目标目录已存在同名文件
When 用户尝试移动笔记
Then 应用禁止静默覆盖
And 提供取消或修改名称的选择
And 两个原文件均保持不变
```

### AC-06：外部编辑冲突

```gherkin
Given 当前笔记在应用内有未保存修改
When VS Code 又修改了磁盘上的同一文件
Then 应用不得自动覆盖任意一方
And 明确提示外部变化
And 用户可以查看差异并选择处理方式
```

### AC-07：删除恢复

```gherkin
Given 用户删除一篇笔记
When 删除操作完成
Then 文件进入可恢复位置
And 应用说明如何恢复
And Git 状态正确显示删除
```

### AC-08：索引损坏恢复

```gherkin
Given 本地索引文件丢失或损坏
When 用户重新打开工作区或执行重建
Then 应用可从原始文件重新生成索引
And 不要求恢复或修改 Markdown
```

### AC-09：Git 安全检查

```gherkin
Given 工作区存在未保存编辑或未提交修改
When 用户执行拉取
Then 应用先展示风险并阻止无提示覆盖
And 不自动执行 reset 或 clean
```

### AC-10：PicGo 上传失败

```gherkin
Given 用户粘贴一张图片并选择 PicGo 上传
When 上传因网络或配置失败
Then 编辑器不插入无效 URL
And 原图片仍可用于重试或改为本地保存
And 日志不包含 OSS 密钥
```

## 15. 测试重点

### 15.1 文件兼容测试

- 中文、空格、括号、方括号、长文件名。
- 大小写只不同的文件名。
- 软链接和工作区外路径。
- 无权限文件、只读文件、突然被删除的文件。
- UTF-8 BOM、异常编码、超长单行、超大 Markdown。
- 损坏 YAML Front Matter 和未知 Markdown 扩展语法。

### 15.2 文件操作测试

- 跨目录移动、目标重名、文件夹循环移动。
- 移动时应用崩溃或磁盘空间不足。
- 外部编辑器与应用同时保存。
- 批量操作部分失败后的回滚与报告。
- 删除恢复、Git 重命名识别和引用更新。

### 15.3 搜索测试

- 中文、英文、大小写、标点、路径、代码片段。
- 标题与正文权重。
- 删除、移动、外部修改后的索引一致性。
- 忽略规则和二进制文件跳过。
- 索引重建前后结果一致。

### 15.4 安全测试

- `../` 路径穿越和 URL 编码绕过。
- 恶意 Markdown HTML、JavaScript URL、SVG 脚本。
- 文件名和提交信息中的 Shell 特殊字符。
- Git/PicGo 命令注入。
- 日志和错误页中的密钥、绝对路径、正文泄露。

## 16. 风险与应对

| 风险 | 影响 | 应对策略 |
| --- | --- | --- |
| 同一文件被多个编辑器同时修改 | 覆盖数据 | 文件版本检测、冲突提示、原子写入、草稿恢复 |
| Markdown 方言不一致 | 预览与 VS Code 不同 | 明确兼容基线、插件化渲染、未知语法不改写 |
| 移动文件导致链接失效 | 知识关系断裂 | 影响预览、可选更新、坏链扫描、可撤销操作 |
| 索引与真实文件不一致 | 搜索漏项 | 文件监听 + 定期校验 + 一键重建 |
| Git 操作复杂化 | 产生冲突或丢失修改 | 只覆盖日常安全操作，危险操作交给 CLI/专业工具 |
| OSS/PicGo 配置泄露 | 安全事故 | 复用外部凭据管理，不写仓库、不记日志 |
| 功能范围快速膨胀 | 项目难以完成 | 先做只读验证版，再按真实使用频率迭代 |
| 将目录规则写死 | 未来结构调整成本高 | 工作流、模板和元数据映射可配置 |
| 应用索引文件进入 Git | 多设备产生噪声和冲突 | 存系统应用数据目录，并提供忽略检查 |
| 本地 Web 服务被其他设备访问 | 隐私泄露 | 默认绑定 127.0.0.1，远程访问另做安全设计 |

## 17. 已确认事项

原待确认事项已于 2026-10-07 全部确认，详细决策见 [02-confirmed-product-decisions.md](02-confirmed-product-decisions.md)。核心结论如下：

1. 首版同步支持 macOS 和 Windows。
2. 先采用本地服务 + Web UI，最终交付一键安装桌面客户端。
3. 首版轻量编辑，长期目标是替代 VS Code 的日常 Markdown 编辑能力。
4. Git 前期固定单 remote，首版只读状态；后期支持多分支，不支持多 remote。
5. 当前使用 VS Code PicGo 插件，上传能力后续通过独立适配器实现。
6. 应用新建笔记必须有 Front Matter。
7. 收藏、最近访问和保存查询需要跨电脑同步。
8. 只管理 NoteHub，不管理同一仓库中的其他历史笔记。
9. 近期需要带认证的局域网/手机/平板只读访问。
10. 财务、工作和账号类笔记需要额外隐藏。
11. 删除默认进入系统废纸篓。

## 18. 建议的下一步

1. 从本文档确认 MVP 范围，尤其是“内置编辑深度”和“Git/PicGo 是否进入首版”。
2. 制作只读验证版低保真原型，先覆盖目录、搜索和预览三个核心页面。
3. 选取 20～30 篇具有代表性的真实笔记建立兼容性测试集，包括中文路径、Mermaid、任务、OSS 图片、本地附件和 Front Matter。
4. 完成一次技术验证：中文全文搜索、文件监听、安全 Markdown 渲染和在 VS Code 中打开。
5. 在仓库副本上实现文件移动与外部修改冲突测试，通过后再允许操作真实 NoteHub。
6. 连续实际使用一至两周，根据高频操作决定第 1 阶段功能，而不是一次性实现全部设想。
